# 许可示例

以下帮助理解 [LICENSE](../LICENSE)，如有出入以 LICENSE 中文正文为准。

项目采用自定义的“小克源码使用许可证 1.0”（原“翻译助手源码使用许可证 1.0”，仅更名、条款不变）。它允许商业开发，只限制没有实质改进的直接转售，不是全面禁止商业使用，也不是限制竞争产品的条款。

| 场景 | 许可边界 |
| --- | --- |
| 自己使用、公司内部使用、免费分享原版 | 允许，分发须保留适用声明 |
| 改应用名称、图标、包名，重新签名后出售 | 不允许；只有表面改动 |
| 仅加支付、会员、订阅或授权码，把原有功能收费解锁 | 不允许；计费功能本身不构成实质改进 |
| 复制完整功能，放到服务器上收费访问，没有实质开发改进 | 不允许；改变交付形式本身不构成实质改进 |
| 实质提升 OCR、排版、速度、稳定性或可访问性后收费 | 允许，不要求改成另一种产品 |
| 实现有实际用途的新功能、重要缺陷修复或交互改进后收费 | 允许，须有可验证且非微小的改进 |
| 把部分代码经过实质整合，用于自行开发的商业产品 | 允许，保留所用代码的适用许可和版权声明 |
| 改进后仍然主要做翻译、继续保留大量原始代码 | 不因此禁止商用 |
| 只更换默认服务地址或模型名，其他实现不变，再收费售卖 | 普通配置变化本身不构成实质改进 |
| 免费提供软件，接受不换取软件获取或功能解锁的自愿捐赠 | 不属于禁止的直接转售 |

“添加广告”本身不算实质改进，但这不意味着本许可证禁止一切广告收入；第 3 条所列的直接转售条件必须同时成立。用其他收费名称掩盖对软件副本、使用权或原有功能的收费，并不能消除限制。

## 如何判断实质性改进

看实际开发成果：功能、性能、可靠性、兼容性、安全性、可访问性或交互体验是否有可验证且非微小的改善。代码行数、修改比例、提交次数和投入工时都不是固定门槛。

保留修改说明、测试结果或前后对比，可以帮助其他人理解改进；许可证不要求把这些材料逐次交给原作者审核，也不强制公开新增或修改的源码。

## 分发时需要做什么

- 随附 LICENSE，保留所包含代码的版权和第三方声明。
- 合理标明修改版身份，不冒称为原作者发布或背书。
- 二进制分发可在随附文档或应用内许可证页面提供声明。
- 不得把仍受本项目许可约束的代码重新标注为不受限制的 MIT / Apache 代码。
- 第三方依赖和素材的权利不会因采用本项目许可证而改变。
